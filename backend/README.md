# AEC Compliance Portal — Flask Backend

Production-ready Flask backend for the AEC Compliance Portal React frontend.

> **Status:** Foundation + tooling + models + PostgreSQL schema + seeding.
> No auth, no CRUD, no frontend integration yet. This establishes the
> application skeleton, configuration, extensions, CORS, standardized response
> envelopes, JSON error handlers, rate limiting, the full 14-table data model,
> the PostgreSQL schema via Flask-Migrate, and idempotent CLI seeding
> (`flask create-admin`, `flask seed-demo`).

## Getting Started

### 1. Create and activate a virtual environment

```bash
python -m venv venv
```

- Windows (PowerShell): `venv\Scripts\Activate.ps1`
- Windows (cmd): `venv\Scripts\activate.bat`
- macOS/Linux: `source venv/bin/activate`

### 2. Install dependencies

```bash
pip install -r requirements.txt
```

### 3. Configure environment variables

```bash
copy .env.example .env     # Windows
cp .env.example .env       # macOS/Linux
```

Edit `.env` and set real values (especially `SECRET_KEY`, `JWT_SECRET_KEY`,
`DATABASE_URL`, and `CORS_ORIGINS`). Never commit real secrets.

### 4. Start the backend

```bash
python run.py
```

The API runs at `http://localhost:5000`.

## Database Setup & Migrations

The schema is managed with Flask-Migrate/Alembic against PostgreSQL.

### 1. Create the database

```sql
CREATE DATABASE aec_compliance;
```

Set `DATABASE_URL` in `.env`:

```
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/aec_compliance
```

### 2. Apply migrations

From the `backend/` directory (Windows PowerShell):

```powershell
$env:FLASK_APP="app:create_app"
$env:FLASK_ENV="development"
venv\Scripts\python.exe -m flask db upgrade
```

macOS/Linux:

```bash
export FLASK_APP=app:create_app FLASK_ENV=development
flask db upgrade
```

The initial revision (`552c0ab0a142_initial_schema.py`) creates the 14
business tables, 19 PostgreSQL-native enum types, indexes, and constraints.

### 3. Common migration commands

| Command                     | Purpose                                              |
|-----------------------------|------------------------------------------------------|
| `flask db upgrade`          | Apply all pending migrations (to head)               |
| `flask db downgrade -1`     | Roll back one revision                               |
| `flask db downgrade base`   | Roll back to an empty schema                         |
| `flask db migrate -m "msg"` | Autogenerate a new revision after model changes      |
| `flask db current`          | Show the current revision                            |
| `flask db history`          | List the migration history                           |

Always review autogenerated migration files before applying them, and confirm
new migrations are additive before running them on shared databases.

## CLI Commands

### `flask create-admin`

Creates (or verifies) the portal administrator. Idempotent: on re-run with an
existing admin it does nothing unless `--reset-password` is passed.

The password is read from `--password`, the `AEC_ADMIN_PASSWORD` environment
variable, or an interactive prompt — and is never printed or logged. It must be
at least 8 characters.

```powershell
$env:AEC_ADMIN_PASSWORD="<a-strong-password>"
venv\Scripts\python.exe -m flask create-admin
```

Optional: `--email`, `--name`, `--reset-password`. Defaults come from
`AEC_ADMIN_EMAIL` / `AEC_ADMIN_NAME` (default `info@ansumana.com`).

### `flask seed-demo`

Seeds reference demo data mirroring the frontend seed data (4 proponents,
4 permits, 4 schedules, 4 findings, 1 evidence, 2 bookings, 2 service
requests, 3 notification logs, 2 client users, 1 company settings record).
Idempotent: it skips when demo data is already present.

```powershell
venv\Scripts\python.exe -m flask seed-demo
venv\Scripts\python.exe -m flask seed-demo --force   # clear + re-seed
```

Client accounts use a random password unless `AEC_DEMO_PASSWORD` is set; set
it and re-run with `--force` to assign a known password. Admin accounts are
never touched by `seed-demo`.

## Data Model

Fourteen models are defined under `app/models/` (see `app/models/enums.py`
for the shared enums, which match the frontend `src/types.ts` exactly):

`User`, `Proponent`, `Permit`, `ReportSchedule`, `Finding`, `Evidence`,
`Booking`, `ServiceRequest`, `Notification`, `NotificationLog`,
`CompanySettings`, `File`, `AuditLog`, `PasswordResetToken`.

Key decisions:

- UUID primary keys generated with Python `uuid4`.
- Timezone-aware datetimes via a `UTCDateTime` type (UTC-normalized).
- PostgreSQL-native enum types (falling back to VARCHAR + CHECK on SQLite).
- Soft delete (`is_deleted`/`deleted_at`) on proponents, permits, report
  schedules, findings, evidence, bookings, and service requests.
- `ON DELETE` policy: RESTRICT on proponent-owned records, SET NULL on
  optional references, CASCADE only for notifications and password reset
  tokens owned by a user.
- Passwords are never stored: `User` carries only `password_hash`. Reset
  tokens store only a SHA-256 hash (`password_reset_tokens.token_hash`).
- `File` records metadata only; binary content lives on disk.
- Emails are normalized (lowercased) and unique.

## Response Envelope

All endpoints return a standardized envelope:

- Success: `{"status": "success", "data": ..., "message": ...}`
- Error:   `{"status": "error", "code": ..., "message": ...}`
- Paginated lists: `data = {"items": [...], "pagination": {"page", "per_page",
  "total", "total_pages"}}` (default 25 per page, capped at 100).

HTTP errors (404/405/413/500) are rendered as JSON error envelopes by the
global handlers in `app/utils/errors.py`.

## Running Tests

```bash
pytest
```

Tests use an in-memory SQLite database (or `TEST_DATABASE_URL` if set) and
cover the health endpoint, response envelope, all 14 models, the CLI commands
(idempotency/safety), and a full migration upgrade → downgrade → upgrade
round-trip on a throwaway SQLite file. Production PostgreSQL is never touched
by the test suite.

## Configuration

All configuration is driven by environment variables. See `.env.example` for
the full list (JWT cookie flags, uploads, SMTP mail, WhatsApp, rate limiting,
`AEC_ADMIN_PASSWORD`, `AEC_DEMO_PASSWORD`). Production configuration validates
that required secrets and origins are present and refuses a wildcard
`CORS_ORIGINS`.
